# SSL/TLS Configuration Guide

## Overview

As of this version, Androrat now uses SSL/TLS encryption by default to protect communications between the server and clients. This prevents on-path attackers from:
- Intercepting sensitive data transmitted over the network
- Injecting malicious commands
- Impersonating the server or clients

## Quick Start

### 1. Generate SSL Certificate

For testing purposes, you can generate a self-signed certificate:

**Linux/Mac:**
```bash
chmod +x ssl-setup.sh
./ssl-setup.sh
```

**Windows:**
```cmd
ssl-setup.bat
```

This will create a `keystore.jks` file in the current directory.

### 2. Start the Server

The server will automatically use SSL/TLS if a keystore is present:

```bash
java -jar AndroratServer.jar
```

### 3. Configure Clients

Clients must be configured with the server's certificate to establish trust. See the "Client Configuration" section below.

## Advanced Configuration

### Custom Keystore Location

You can specify a custom keystore location and password:

```bash
java -Dandrorat.keystore.path=/path/to/keystore.jks \
     -Dandrorat.keystore.password=your_password \
     -jar AndroratServer.jar
```

### Disable SSL/TLS (Not Recommended)

**WARNING:** Disabling SSL/TLS leaves your communications vulnerable to interception and tampering.

```bash
java -Dandrorat.ssl.enabled=false -jar AndroratServer.jar
```

## Production Deployment

### Using a Trusted Certificate

For production use, obtain a certificate from a trusted Certificate Authority (CA):

1. Generate a Certificate Signing Request (CSR):
```bash
keytool -certreq -alias androrat-server -keystore keystore.jks \
        -file server.csr -storepass changeit
```

2. Submit the CSR to a Certificate Authority

3. Import the CA's root certificate:
```bash
keytool -import -trustcacerts -alias root -file ca-root.crt \
        -keystore keystore.jks -storepass changeit
```

4. Import your signed certificate:
```bash
keytool -import -trustcacerts -alias androrat-server \
        -file server.crt -keystore keystore.jks -storepass changeit
```

### Security Best Practices

1. **Use Strong Passwords:** Change the default keystore password
2. **Protect the Keystore:** Set appropriate file permissions (chmod 600 on Linux)
3. **Regular Updates:** Renew certificates before expiration
4. **Client Authentication:** The server requires client certificates for mutual authentication
5. **Monitor Logs:** Check for SSL/TLS handshake failures

## Client Configuration

### Android Client Setup

The Android client must be configured to trust the server's certificate:

1. Export the server certificate:
```bash
keytool -export -alias androrat-server -keystore keystore.jks \
        -file server.crt -storepass changeit
```

2. Convert to BKS format (Android's keystore format):
```bash
keytool -importcert -v -trustcacerts -file server.crt \
        -alias androrat-server -keystore client-truststore.bks \
        -provider org.bouncycastle.jce.provider.BouncyCastleProvider \
        -providerpath bcprov.jar -storetype BKS -storepass changeit
```

3. Include the truststore in the Android app's assets

4. Update the Android client code to use the truststore

### Client Certificate Generation

For mutual authentication, generate client certificates:

```bash
keytool -genkeypair -alias androrat-client -keyalg RSA -keysize 2048 \
        -validity 365 -keystore client-keystore.jks -storepass changeit \
        -dname "CN=Androrat Client, OU=Mobile, O=Organization"
```

Export and import into the server's truststore:
```bash
keytool -export -alias androrat-client -keystore client-keystore.jks \
        -file client.crt -storepass changeit

keytool -import -trustcacerts -alias androrat-client -file client.crt \
        -keystore keystore.jks -storepass changeit
```

## Troubleshooting

### SSL Handshake Failures

If you see SSL handshake errors:

1. Verify the keystore exists and is readable
2. Check the keystore password is correct
3. Ensure the certificate hasn't expired
4. Verify client and server certificates are properly configured

### Certificate Verification Errors

If clients can't verify the server certificate:

1. Ensure the client has the server's certificate in its truststore
2. Check that the certificate's Common Name (CN) matches the server hostname
3. Verify the certificate chain is complete

### Performance Issues

SSL/TLS adds computational overhead. For high-traffic scenarios:

1. Use hardware acceleration if available
2. Consider using ECDHE cipher suites (already enabled by default)
3. Monitor CPU usage and adjust accordingly

## Technical Details

### Enabled Protocols
- TLS 1.2
- TLS 1.3 (if supported by JVM)

### Enabled Cipher Suites
- TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
- TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
- TLS_DHE_RSA_WITH_AES_256_GCM_SHA384
- TLS_DHE_RSA_WITH_AES_128_GCM_SHA256

These cipher suites provide:
- Forward secrecy (ECDHE/DHE)
- Strong encryption (AES-256/128-GCM)
- Authenticated encryption (GCM mode)

### Mutual Authentication

The server requires client authentication (`setNeedClientAuth(true)`), meaning:
- Clients must present a valid certificate
- The server verifies the client certificate against its truststore
- Only authenticated clients can connect
